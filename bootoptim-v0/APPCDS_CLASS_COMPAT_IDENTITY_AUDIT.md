# AppCDS class-compatibility identity audit

Agent 207 diagnostic candidate.

## Base and scope

This branch is stacked exactly on PR #59 head

(codex/ntfs-usn-long-name-buffer). It does not modify PR #56, #57, #58 or #59,

The current v0 launch plan uses one SHA-256 for two different concepts:

1. class/archive compatibility; and
2. ordinary profile state.

part2.rs recursively includes every regular file below config, defaultconfigs,
kubejs and scripts in pack_inputs, then combines those files with mod JARs and
resource-pack selection. part1.rs uses the resulting complete plan SHA for
training reconciliation, READY classification, promotion and reuse. Therefore
an ordinary profile-value change currently has the same invalidation power as
a JDK, classpath, mod JAR or transformer-input change.

## Why the split cannot be a filename allowlist

AppCDS stores archived class metadata. Ordinary runtime configuration is not by
itself a reason to invalidate an archive, but configuration can indirectly
change class definitions.

The exact BootOptim integration demonstrates both sides of that boundary:

- BootOptim publishes an ITransformationService. Its transformers() method
  returns an empty list. Its early config/boot_optim.properties startupLog
  setting controls diagnostics, not a transformer set.
- BootOptim's own Mixin configuration is packaged in the mod JAR and has no
  IMixinConfigPlugin entry.

Those facts support treating that specific BootOptim gameplay/diagnostic value
as class-definition-neutral, but they do not prove the same thing for other
mods. ModLauncher transformation services and Mixin plugins are arbitrary code.
An IMixinConfigPlugin can decide whether a mixin applies to a target, and a
transformation service can construct transformers conditionally. Either can
read configuration through helper classes, reflection, system properties,
native code or another loader.

For that reason this diagnostic never promotes negative heuristic evidence into
compatibility. File extensions, names, cosmetic/gameplay labels and absence of
an obvious config string are discovery aids only.

## Exact-pack inventory tool

bootoptim-v0/tools/audit_class_compat_inputs.py consumes the pinned public
BootOptim exact-pack ZIP directly. For every top-level mod JAR it records:

- JAR SHA-256;
- ModLauncher service-provider metadata, including ITransformationService and
  ILaunchPluginService providers;
- MixinConfigs manifest entries;
- NeoForge/legacy mods.toml mixin declarations;
- mixin-looking JSON configs and their plugin field;
- coremods/access-transformer metadata;
- a bounded static string scan of declared transformation-service,
  launch-plugin and Mixin-plugin entrypoint classes for likely external-input
  references.

It also inventories the presence/count/extensions of config, defaultconfigs,
kubejs and scripts plus options.txt.

The output statuses are deliberately non-authorizing:

- unresolved-dynamic-hook: source/manual audit is required;
- unresolved-parse-error: uncertainty remains and must fail closed;
- static-transform-metadata-only: only known static metadata was observed, but
  this is not a global proof that external config is irrelevant;
- no-known-transform-metadata-observed: no known hook was found, also not proof
  of compatibility.

Reflection, delegation, generated classes, native code, indirect config readers
and non-standard loaders are explicit limitations. A future runtime policy must
treat unresolved inputs as STOCK, not silently compatible.

## Recommended identity model after audit closure

The launch plan should retain two domains instead of one invalidation hash.

### class_compat_sha256

The consumption/training authority should cover at least:

- exact Java executable/path/release identity;
- CDS-relevant and transformation-relevant JVM arguments and hidden JVM option
  environment policy;
- ordered classpath and module-path;
- mod JAR identities;
- loader/transformation-service/Mixin configuration as represented by those
  JARs;
- external files proven to influence transformer registration, Mixin
  applicability, generated bytecode or equivalent class-definition decisions;
- existing helper/launcher/version fields needed by the v0 compatibility
  contract.

training.meta and ready.meta should be schema-bumped to bind to this class
compatibility digest. Existing locks, tombstones, clean-exit marker,
promotion rules, archive SHA-256/size validation and stock fallback must remain
unchanged.

### profile_state_sha256

Gameplay/profile state can be recorded separately for diagnostics or profile
management without gating READY when it is proven not to affect class
definitions. This includes ordinary gameplay values, whether cosmetic or not;
the semantic question is class transformation, not user-visible importance.

The full profile-state digest should not force the regular HDD preflight to
enumerate/hash every config file. Once the transformation-input table is
complete, normal AppCDS preflight should walk/hash only class-compatibility
inputs. A full profile-state snapshot can be lazy/diagnostic or maintained by a
separate profile mechanism. This is the route that removes the config-tree HDD
cost rather than merely omitting its final digest.

## Conservative treatment pending exact-pack audit

- config/defaultconfigs: do not globally include every value in class
  compatibility, but do not globally exclude them until every dynamic hook is
  resolved. Promote only source-proven external transformer inputs into
  class_compat_sha256.
- kubejs/scripts: keep conservative class-compatibility treatment until their
  exact engines and pack scripts are audited. They are executable/dynamic
  inputs and may generate or condition code indirectly.
- resource-pack selection: it is resource state rather than ordinarily a JVM
  class-definition input, but keep it conservative until dynamic hooks are
  audited for early resource/options reads. Do not infer safety merely from the
  normal Minecraft resource-loading phase.

## Tests required before runtime semantics change

A later behavioral PR should prove all of the following while preserving the
existing v0 state machine:

- changing a source-proven ordinary gameplay value changes profile state but
  preserves class_compat_sha256 and an otherwise valid READY archive remains
  consumable;
- changing a mod JAR, JDK, relevant JVM argv, classpath/module-path ordering or
  audited transformer-affecting input changes class_compat_sha256 and cannot
  consume the old archive;
- an unresolved/malformed transformation-input classification is ineligible and
  returns STOCK;
- a mismatch during training still tombstones the untrusted campaign;
- archive hash/size corruption still cannot be consumed;
- incremental USN digest reuse remains an optimization of hashing only and
  cannot change identity semantics.

Hosted CI can validate tooling/software behavior only. It is not HDD
performance evidence and it does not establish how many classes HotSpot loaded
from an AppCDS archive.
